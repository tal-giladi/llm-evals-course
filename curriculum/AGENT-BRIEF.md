# Writing brief — modules and lessons

Binding on every lesson and quiz in this course. `plan.md` and
`tals-academy/docs/new-course-instructions.md` are the sources; this file is the working summary.

## Non-negotiable rules

1. **Plain markdown and YAML only.** No React, JSX, MDX, no npm, no generated HTML, no content that
   exists only after JavaScript runs.
2. **English only. UTF-8. LF line endings.**
3. **Markdown must stand alone.** Never depend on docsify, localStorage, cookies or a progress script.
4. **No lesson ever calls a progress tool.** The Academy tracks progress itself.
5. **Paths are stable ids.** Never renumber a lesson. MM restarts at 01 in every module.
6. **Relative links only** (`../module-04/lesson-02.md`). No absolute GitHub or Pages links, no
   docsify-style `#/…`, no `?id=`, no `:include`.
7. **Allowed raw HTML:** `<details>`/`<summary>`, `<kbd>`, `<sub>`, `<sup>`, `<br>`. Nothing else —
   no `<div class=…>`, no `<script>`, no `<iframe>`, no inline `<svg>`, no `on…=` handlers.
8. **No "Knowledge check" / "Quiz" / "Assessment" section in the markdown.** The quiz lives only in the
   `.quiz.yaml`. Never write an `## Answers` or `# Answer Key` heading.
9. **One H1**, right after the front matter: `# NN.M · Title` (middle dot, spaces around it).
10. **Right after the H1, exactly one plain paragraph** — not a heading, list, bold line or HTML. It
    becomes the summary on the module page.
11. Allowed markdown: GFM tables, task lists, footnotes, fenced code with a language, `$…$` and `$$…$$`
    math, ```mermaid```, images, and GitHub alerts `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`,
    `> [!WARNING]`, `> [!CAUTION]`.

## Lesson file

Path: `lessons/module-NN/lesson-MM.md`

```markdown
---
id: "07.3"
module: 7
minutes: 15
practice_minutes: 40
prerequisites: ["07.2", "04.4"]
objectives:
  - A measurable objective, phrased as what the learner can do.
  - A second one.
volatility: concept
sources:
  - title: "Primary source title"
    url: https://example.org/paper
last_verified: "2026-10-01"
---

# 07.3 · Lesson title

One plain intro paragraph that becomes the summary.
```

- `volatility` is `concept` unless the lesson is about a specific tool or API, then `implementation`.
- Every id in `prerequisites` must be a real lesson id that comes **earlier** in the course.
- `last_verified` is `"2026-10-01"`.

## Section template — use these exact `##` headings, in this order, in every lesson

The course uses one fixed section set. Keep it identical across all 43 lessons.

1. `## Why it matters` — the **failure**: a real case where the usual approach gives the wrong answer.
   Open with what breaks and who notices.
2. `## How it works` — the mechanism. Include a small worked example with real numbers you can check
   by hand (a kappa over 10 items, a Wilson interval, a swap test, a confusion matrix).
3. `## Show me` — a recorded run from the lab that demonstrates the effect. Quote numbers that the
   simulation actually produces.
4. `## Try it` — **Predict first**, in bold, then the simulation link on its own line, then 2–5
   guided experiments on dev items.
5. `## Break it` — set the knob so the eval lies. Name the lie.
6. `## Fix it` — the change that repairs it, described on the scoreboard.
7. `## How do I know it works?` — **Challenge**: reach a target on dev, then one held-out validation.
8. `## Use / don't use` — in production: cost, latency, what teams actually do.
9. `## Reflect` — one or two questions to answer in writing.
10. `## Sources`

Use `###` inside sections. Wrap a reference solution in `<details>`/`<summary>`.

## Simulation links

Exactly this form, on a line of its own, the link text starting with `Simulation:`:

```markdown
[Simulation: judge-lab](../../simulations/judge-lab/index.html?preset=tnr)
```

Use the exact simulation folder and preset from the module table you are given. **Only use presets that
exist** for that simulation — if you are unsure, open the simulation's `app.js` and read `PRESETS`.

Every lab carries an "educational model" banner: the judge runs are generated by a seeded model, not by
a real LLM. Where a lesson quotes a judge number, do not present it as a measurement of a named model
in the wild.

## Quizzes

Path: `lessons/module-NN/lesson-MM.quiz.yaml` — **3 to 5 questions**.

```yaml
- id: q1                    # unique in this file, never reused for a different question
  question: >-
    A pod keeps restarting and `kubectl logs` shows nothing. What do you check first?
  options:
    - The logs of the previous container instance with `kubectl logs --previous`.
    - The node's disk usage, since full disks always cause silent restarts.
    - The service definition, because missing endpoints cause all restarts.
    - The image tag, because `latest` is re-pulled on every restart.
  correct: 0                # 0-based index into options
  explanation: >-
    The current container just started, so its log is empty; `--previous` shows the
    output of the one that crashed, which usually names the cause.
```

- Exactly **4 options**, exactly **one** correct, `correct` is 0–3. Single answer only.
- Spread `correct` across 0–3 in every file (roughly a quarter each, no pattern).
- Wrong options are plausible mistakes someone who skimmed would make — never jokes, never absurd, and
  never obviously longer or more hedged than the correct one.
- All four options have similar length and tone.
- No "all of the above" or "none of the above".
- `explanation` is required and teaches in 1–3 sentences.
- No `source:` field.
- Use `>-` block scalars for any text containing `:`, `#`, quotes or backslashes.
- Questions must be answerable from the lesson, and must test reasoning rather than recall.

Module quizzes live at `assessments/module-NN-quiz.md` (a short intro page, no questions, no answers)
and `assessments/module-NN-quiz.quiz.yaml` (**8–10 scenario questions**, same format).

## Voice

Write for a working developer who does not know statistics. Every concept gets a concrete failure that
motivated it, not a definition followed by an example. Prefer "on 40 items, that difference is inside
the interval, so it is not evidence" over "statistically insignificant". Give the reason, not the rule.

Never claim a statistical result without the sample size behind it. When you quote a number from the
lab, it must be one the lab actually produces on the items described.
